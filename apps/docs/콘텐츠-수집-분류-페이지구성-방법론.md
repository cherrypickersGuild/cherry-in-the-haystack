# 콘텐츠 수집·분류 및 페이지 구성 방법론

Cases 그룹을 만들며 반복된 혼동(기사 vs 도메인, 위계 착오)을 겪고 바로잡은 결과를 표준 절차로 정리한다.
Research & Models, Discourse 등 **다른 그룹을 만들 때도 이 문서를 그대로 따른다.**

---

## 0. 3대 원칙

1. **의미를 먼저 정의한다.** "카드가 8개 나오나"(모양)가 아니라 "이게 기사냐 도메인이냐"(의미)를 먼저 확정한다. 자료의 성격 정의 → 그에 맞는 축·형식 선택 → 검증 순서를 건너뛰지 않는다.
2. **지어내지 않는다.** 요약·데이터는 실제 원문에서만. 못 구하면 폴백하거나 비운다. 목업/추정 금지.
3. **하드코딩 금지, 전부 JSON 구동.** 제목·문구·색·탭·카드 구성·도메인 정규화는 모두 JSON에서 읽는다.

## 1. 자료조사 (수집) — 가장 중요

### 1.1 모든 항목은 수집 시점에 `kind`로 분류한다

한 항목이 **기사(article)** 인지 **도메인(domain)** 인지를 **초기조사 JSON에 반드시 명시**한다. 나중에 붙이지 않는다. 이게 없으면 혼합 분류를 절대 제대로 못 나눈다.

| kind | 뜻 | 판별 기준(`source_type`) | 표현 형식 |
|---|---|---|---|
| `article` | ~에 관해 쓴 글 (블로그/논문/발표) | `engineering-blog` · `blog` · `conference` · `paper` | 기사형 (목록) |
| `domain` | ~에 AI를 적용한 제품/응용 그 자체 | `product` | 도메인형 (랜드스케이프) |

> 기사의 "도메인"은 회사 업종을 우연히 빌려온 메타일 뿐, 글의 본질이 아니다.
> 도메인 항목의 "도메인"은 존재 이유 그 자체다. **둘을 같은 방식으로 표현하면 안 된다.**

### 1.2 초기조사 JSON 스키마 (`apps/web/public/<group>/entities.json`)

```jsonc
{
  "id": "…",
  "category": "case-studies | domain-applications | product-discovery",
  "kind": "article | domain",          // ★ 수집 때 명시 (1.1)
  "domain": "원본 도메인/산업",          // 그룹핑 축
  "name": "제목/제품명",
  "company": "회사/벤더 | null",
  "description": "짧은 한 줄(원본)",
  "summary": "실측 요약 2~3줄(1.3) — 없으면 필드 생략",
  "tags": ["…"],
  "source_type": "engineering-blog | blog | conference | paper | product",
  "url": "원문 링크",
  "date": "YYYY | null",
  "source": "수집 출처(큐레이션 리스트명)"
}
```

### 1.3 요약(summary)은 실측만 — 소스별 단계적

- **① 웹 메타**: `og:description` → `twitter:description` → `meta[name=description]` → JSON-LD `description` 순. 봇 차단(예: medium)엔 `facebookexternalhit/1.1` UA가 통한다.
- **② 도메인 전용 API** — 웹 메타가 없는 소스용. 예) 논문은 URL이 arxiv **PDF**라 메타가 없으므로 **arxiv API**(`export.arxiv.org/api/query?id_list=<id>` 또는 `search_query=ti:"제목"`)로 초록을 받는다. arxiv에 없으면 **Semantic Scholar**(`.../graph/v1/paper/search?...&fields=abstract`). 둘 다 레이트리밋 → 저동시성·수 초 간격 필요. (상세: [`자료조사-Research.md`](./자료조사-Research.md) §4)
- **못 구하면 지어내지 말고** `description`(짧은 한 줄)로 폴백. 커버리지를 정직하게 보고한다(예: cases 76% · papers 60/62). **추정/생성 금지.**

### 1.4 분류 판정 (category 단위)

수집 후 category별로 kind 분포를 세어 **기사 단일 / 도메인 단일 / 혼합** 을 판정한다.

| 예 (Cases) | article | domain | 판정 | 페이지 형식 |
|---|---|---|---|---|
| case-studies | 543 | 0 | 기사 단일 | 기사형 |
| domain-applications | 43 | 104 | **혼합** | 두 섹션 분리 |
| product-discovery | 101 | 123 | **혼합** | 두 섹션 분리 |

## 2. 위계 (페이지 상위 구성)

Engineering(빌딩블락)이 기준. **상위 1층 + 하위 서브**.

```
그룹 (예: Cases)  ── 사이드바 그룹 헤더
├─ [상위] 블록 페이지 (그룹 랜딩 카탈로그)      ← 헤더 클릭 시. 전체를 도메인별로 다 나열 + 펼치기.
│                                              (Engineering의 "Building Blocks" 자리)
└─ [하위] 서브 페이지들 ── 각 분류. 형(型) 두 가지:
   ├─ 기사형(article)  : pill 섹터 탭 + 기사 세로 목록
   ├─ 도메인형(domain) : 8 도메인 카드 × 베스트 5 + 카드 클릭 → 모달
   │                     (= Frameworks Best와 동일한 LandscapeSection)
   └─ 혼합(mixed)      : 한 페이지 두 섹션
                         ① 위: 도메인형 랜드스케이프 (kind=domain)
                         ② 아래: 기사형 목록 (kind=article)
```

**흔한 위계 착오(하지 말 것):**
- "도메인별로 카드를 전부 나열 + 펼치기"는 **상위 카탈로그가 하는 일**이다. 이걸 서브에 만들면 위계가 한 칸 위로 어긋난다(카탈로그 중복).
- 진짜 "도메인형" 서브 = **베스트 5만 큐레이션**하는 랜드스케이프.

### 2.1 페이지 내부 구성 규칙
- **Rising Star**: 도메인형·혼합 서브 페이지 **맨 위**에 1개. 랜드스케이프에 stars가 있으면 최다 스타, 없으면(도메인형 등) **대표(첫) 항목을 "Featured pick"**으로. (`RisingStar` 컴포넌트, stars 없을 때 fallback 내장.)
- **섹션 순서**: 기사형 목록은 **제목(예: "Related Articles")을 pill 탭 위**에 둔다. 안 그러면 탭이 라벨 없이 튀어나와 무슨 섹션인지 모른다.
- **비-JSON 섹션 숨김**: DB 등 JSON 구동이 아닌 콘텐츠(예: Frameworks의 Recent Updates)는 JSON 기사형으로 전환하기 전까지 **숨긴다**. 형식이 뒤섞이면 안 된다.
- **컴포넌트 재사용**: 기사형=`CasesArticleList`(prop `base`로 그룹 전환: cases/research/discourse), 도메인형=`LandscapeSection`(공용, `pageKey`로 `/api/<page>/landscape` 조회). 그룹마다 새로 만들지 말고 재사용.
- **대표 픽(Featured)**: 기사형 서브 페이지 **맨 위**에 대표 1개(스타 지표가 없으니 데이터로 점수화). 공용 로직 `FEATURED_CFG` — 날짜 있으면 최신 연/분기 pool, 없으면 전체 pool → **요약(+5)·인기주제(+3)·인지도 회사(+2)·유명 엔티티(+4)** 점수 최고 1개(결정적). 카테고리마다 라벨·가중 집합만 다름. 각 그룹 자료조사 문서에 기준을 기록해 **재수집 시 자동 재선정**되게 한다.

  ⚠️ **보완점(공통)**: `FEATURED_CFG`(prominent/notable/trending 집합·라벨)가 **코드에 하드코딩**돼 있어 방법론의 "JSON 구동" 원칙과 어긋난다 → `pages.json`로 이전하면 코드 수정 없이 기준 갱신 가능. 또 **요약 품질 필터**(저자 나열형 감점 등)를 공용화하면 픽 품질↑.

## 3. 하위 구성요소 (컴포넌트 & 데이터 흐름)

### 3.1 JSON 3층 (단일 소스, 하드코딩 금지)

| 파일 | 역할 |
|---|---|
| `public/<group>/entities.json` | **기초조사** — 데이터 + `summary` + `kind` |
| `public/<group>/icons.json` | **아이콘·색** — 8색 팔레트, 테마 이모지 풀 |
| `public/<group>/pages.json` | **페이지 구성** — 분류별 title·subtitle·탭·카드필드·**도메인 정규화 맵(domainMap)**·source_type 라벨 |

### 3.2 컴포넌트 (Cases 실제 예)

| 형식 | 컴포넌트 | 데이터 경로 |
|---|---|---|
| 상위 카탈로그 | `NDCasesPage` (`nd-cases-page.tsx`) | `entities.json` (client) |
| 기사형 | `CasesArticleList` / `NDCasesListPage` (`nd-cases-articles-page.tsx`) | `entities.json` (client, `kind` 필터) |
| 도메인형·혼합 | `NDCasesBestPage` (`nd-cases-best-page.tsx`) → `LandscapeSection` (`nd-landscape.tsx`) + `CasesArticleList` | 랜드스케이프는 **백엔드 API**, 기사는 client |

- `CasesArticleList({ page, kind, header, sectionTitle })` — 기사 섹션(탭+목록) 재사용 조각. 혼합 페이지 하단에 `kind="article"`로 삽입.
- `NDCasesBestPage`(혼합) = LandscapeSection(도메인) + CasesArticleList(기사) 두 섹션.

### 3.3 도메인형 랜드스케이프 데이터 파이프라인

```
entities.json ──(generate-cases-landscape.cjs)──▶ DATA_DIR/<cat>/<cat>-landscape.json ──(GET /api/<cat>/landscape)──▶ LandscapeSection
```

- 생성 스크립트 규칙:
  - **`kind === "domain"` 항목만** 랜드스케이프에 넣는다(기사는 제외 → 하단 목록으로).
  - `pages.json`의 `domainMap`으로 도메인을 **정규화**해 묶는다(파편화 방지).
  - fallback 버킷(`Other`)은 실도메인이 아니므로 **카드에서 제외**.
  - 상위 8 도메인 × 베스트 5. 카드/항목 텍스트는 `summary || description`.

### 3.4 도메인 정규화 (파편화 방지)

원본 도메인이 65개처럼 잘게 쪼개지면 `pages.json`의 `domainMap`으로 ~15개 정규 도메인에 묶는다(예: `Software Dev`·`Web Development`·`IT` → `Software & IT`). 매핑 안 된 값은 `fallbackLabel`(`Other`)로. **맵은 JSON에만, 컴포넌트엔 없다.**

## 4. 표준 워크플로 (새 그룹/분류 추가 시)

1. **자료조사** — 실제 큐레이션 소스에서 수집. **각 항목 `kind` 명시** → `entities.json`. 요약은 실측 스크래핑(1.3).
2. **판정** — category별 기사/도메인/혼합 판정(1.4).
3. **JSON 구성** — `pages.json`에 분류별 title·subtitle·tabs·card·(필요 시)domainMap·라벨. `icons.json` 팔레트.
4. **도메인형이 필요하면** generate 스크립트로 랜드스케이프 생성(kind=domain, 정규화, best5) → 백엔드가 서빙.
5. **라우팅/위계** — 상위 카탈로그(그룹 랜딩) + 서브(형별). taxonomy의 `landingId`로 그룹 헤더 랜딩 지정.
6. **검증** — 화면에서 위계·형식·데이터가 맞는지 직접 확인.

## 5. 하지 말 것 (실제로 겪은 실수)

- ❌ **기사를 도메인으로 위장** — 회사 업종을 "도메인"이라 부르며 도메인 카탈로그처럼 표현.
- ❌ **혼합을 한 형식으로 뭉개기** — 기사와 도메인이 섞였는데 똑같이 나열. → 두 섹션으로 분리.
- ❌ **서브에 카탈로그 중복** — "전부 나열 도메인 섹션"을 서브에 만들기(그건 상위 블록 페이지의 일).
- ❌ **요약 지어내기** — 못 긁으면 폴백. 추정 금지.
- ❌ **kind를 나중에 붙이기** — 수집 시점에 명시하지 않아 혼합을 못 나눔.
- ❌ **모양만 보고 검증** — 카드 개수·색만 보고 넘어가기. 의미(기사/도메인)를 봐야 한다.
