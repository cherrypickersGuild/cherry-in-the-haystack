# 개념 페이지 제작 지침 (Concept Page Playbook)

> 한 개념(RAG, Embedding, Reranking …)을 **한 페이지**로 만드는 규칙.
> 이 문서만 읽고 다른 에이전트가 **다른 주제로 같은 품질**을 내는 것이 목표다.
> 표준 사례: RAG 페이지(2026-09). 모든 규칙은 그 제작 과정에서 **실제로 지적받아 고친 것**을
> 뒤집어 적었다. 규칙마다 〈왜〉에 근거가 있다.

---

## 0. 이 작업이 무엇인가 (먼저 읽는다)

**개발자 교육 자료다.** 임의로 지어내면 안 된다.

- **기초 자료는 개념 온톨로지다.** 개념 이름·하위 개념·관계는 전부 온톨로지(Postgres `handbook.concept*`)에
  이미 있다. 그것이 정본이고, 페이지는 그것을 옮긴 것이다.
- **이 작업은 새로 쓰는 일이 아니라 고치는 일이다.** 온톨로지에 있는 내용의 **품질을 높이고
  정확도를 끌어올리는 수정 작업**이다 — 그림으로 압축하고, 문장을 사람 말로 다듬고,
  원논문에서 확인한 사실·수치를 붙인다.
- **추정 금지.** 온톨로지를 읽지 않고 "이쯤 되겠지"로 채운 항목은 전부 틀린 것으로 본다.
  〈왜〉 Advanced Prompting의 하위 개념 8개를 추정으로 썼는데, 온톨로지의 실제 자식은 11개였고
  그중 4개만 맞았다. Reflexion·SelfAsk·PlanAndSolve·PAL·ProgramOfThoughts·PromptChaining이
  빠지고, 없는 개념(Least-to-Most·Prompt Optimization)이 들어가 있었다.
- **화면 구조도 정본이 있다.** 로드맵·구획·관계 종류는 `concept-reader-page.tsx` 와
  `lib/api.ts` 가 정본이다. 목업은 그것을 옮긴 것이고, 새로 설계하는 자리가 아니다 (§6-1-1).
- 모르면 **코드와 DB를 먼저 읽는다**(§6-1 쿼리 · §6-1-1 표). 그래도 모르면 **묻는다.**

## 0-A. 산출물 정의 — 무엇을 만드는가

| 항목 | 값 |
|---|---|
| 형식 | **자기완결 HTML 한 장** (외부 CSS·JS·이미지 없음, SVG는 인라인) |
| 파일 위치 | 작업 중에는 스크래치패드, 확정되면 `apps/docs/learning-visual/mockups/<개념>.html` |
| 전달 | Artifact로 발행하고 **링크를 준다**. 같은 파일 경로로 재발행하면 같은 링크가 유지된다 |
| 디자인 원본 | `apps/web/components/cherry/concept-reader-page.tsx` — 색·간격·구조를 **그대로** 가져온다. 새로 디자인하지 않는다 |
| 우측 패널 | `Learning Roadmap`(범례 4줄 포함)을 원본 그대로 살린다 |
| 서버 | 띄우지 않는다. 확인은 발행된 링크로 한다 |

### 0-A-1. 페이지 구성 (순서·이름 고정)

| 구획 | 내용 | 분량 |
|---|---|---|
| `01 — Overview` | 개념 정의 + 그래서 달라지는 것 | **2문장 내외** (줄 수가 아니라 문장 수다) |
| `02 — Flash` | 그림 **넉 장** | 2열 격자 |
| `03 — Cherries` | 인용문 | **5개 이하** |
| `04 — Child Concepts` | 하위·선행·관련 개념 | 온톨로지 그대로 |
| `05 — References` | **외부 링크만** | 4개 |

- 구획 이름은 **영문 고정**이다. 한국어로 바꾸지 않는다.
  〈왜〉 구획명까지 번역하면 원본 개념 페이지와 어긋난다.
- 새 구획을 만들거나 이름을 바꾸려면 **사용자에게 묻는다**(§9 승인 게이트).

## 1. 자료조사

### 1-1. 출처 등급 — 위에서부터 쓴다

| 등급 | 무엇 | 쓰임 |
|---|---|---|
| A | **원논문** | 문제·기여·동작·수치의 정본 |
| B | **저자 본인의 글·인터뷰·팟캐스트** | 체리 후보 |
| C | **소장 도서** (보유 서적) | 체리·해설 |
| D | **수치가 있는 기술 블로그** (Anthropic·NVIDIA 등) | 오늘의 수치 |
| E | 2차 해설·요약 | **인용 금지.** 길 찾기용 |

**등급만으로 통과시키지 않는다 — 주제 거리도 기준이다.**

- 체리 20개 중 **15개는 인공지능 관련 논문·발언에서만** 가져온다. 그 개념을 직접 다룬 글,
  또는 그 분야 사람이 그 개념에 대해 한 말이어야 한다.
- 나머지 **5개(자유 묶음)만 범위를 넓게** 잡을 수 있다 — 인공지능 밖의 글도 된다.
  대신 **후보 표에 그 사실을 표시한다** (`범위` 열에 `AI 밖`, 무슨 분야인지 함께).
- 범위를 넓힌 5개도 사용자가 고르지 않으면 페이지에 싣지 않는다.
  〈왜〉 Strathern(1997, 영국 대학 감사 제도를 다룬 인류학 논문)을 "문장이 좋고 A급 원문"이라는
  이유로 Evaluation 체리에 넣었다. 인공지능 평가와 무관한 글이었고, 표시도 없었다.
  **모자란 칸은 주제 안에서 더 찾아 채운다. 밖에서 끌어와 메우지 않는다.**

### 1-2. 반드시 확보할 다섯 가지

1. **원논문 서론이 첫 문단에 든 문제** → PROBLEM 근거
2. **논문의 핵심 기여 한 문장** → IDEA 근거
3. **동작의 기술적 사실** (조각 크기, 색인 규모, k값, 결합 방식) → SOLUTION 근거
4. **주장을 증명한 실험 수치 + 실험 조건** → BENEFIT 근거
   예: `2018년 질문 × 2016 색인 = 4%`, `2018년 질문 × 2018 색인 = 68%`
5. **사람의 말 20개** → 체리 후보. 추리기 전에 폭을 채운다 (§5-1).
   찾을 때부터 §5-0의 세 축(예지·영감·재치)을 기준으로 본다 — 논문 초록의 건조한 문장만
   모으면 후보 20개가 전부 2점 이하가 된다. 인터뷰·팟캐스트·강연·트윗을 함께 뒤진다.

### 1-3. 언제 멈추나 (중단 조건)

- A급 1개를 **끝까지** 읽었고, 위 다섯 가지가 **전부** 채워졌으면 멈춘다.
- 4번(수치)이 A급에 없으면 D급에서 **최대 2개**까지 찾는다. 그래도 없으면
  BENEFIT을 수치 없이 구성하고, **수치가 없다는 사실을 인계에 적는다.**
- 5번은 **20개를 채우면 멈춘다.** 20개가 안 나오면 나온 만큼만 들고 간다 — 모자란 수를 채우려
  2차 출처에서 퍼오지 않는다.
- **금지**: 같은 사실을 여러 2차 출처로 재확인하며 시간 쓰기.

### 1-4. 검증 규칙

- 인용문과 수치는 **원문에서 직접 확인**한다. 검색 스니펫만 보고 쓰지 않는다.
  〈왜〉 스니펫은 수치를 뭉개고, 저자가 하지 않은 말을 섞는다.
- 2차 출처에서 본 수치는 **1차로 거슬러 올라가** 확인한다. 못 올라가면 버린다.
- 원문이 유료·차단이면 **읽히는 미러**를 찾아 그 URL을 쓴다.
- 확인 못 한 문장은 **버린다.** 그럴듯하게 다듬어 쓰지 않는다.
- 회사가 쓴 글의 문장은 체리로 쓰지 않는다(사람 말이 아니다). 캡션 근거로만 쓴다.

## 2. 선정 — 조사한 것을 다 넣지 않는다

### 2-1. 네 칸 매핑

| 칸 | 무엇 | 고르는 기준 |
|---|---|---|
| PROBLEM | 이 기술이 없을 때 벌어지는 일 | **원논문이 첫 문단에 든 것** |
| IDEA | 발상의 전환 하나 | 논문의 기여 문장 |
| SOLUTION | 실제 동작 | 질문이 들어와 답이 나오기까지 |
| BENEFIT | 달라지는 것 | **수치로 증명된 것만** |

역할 태그는 **영문 고정**(`PROBLEM` `IDEA` `SOLUTION` `BENEFIT`).

### 2-2. 네 칸이 안 맞는 개념이면

문제-해결 구조가 약한 개념(Embedding, Chunking처럼 **구성 요소**인 것)은 아래 틀을 쓴다.
넉 장·2열·격자 규칙은 그대로다.

| 대안 틀 | 네 칸 |
|---|---|
| 구성 요소형 | `WHAT` (무엇인가) · `HOW` (어떻게 만드나) · `CHOICE` (무엇을 고르나) · `IMPACT` (뭐가 달라지나) |
| 비교형(A vs B) | `A` · `B` · `TRADE-OFF` · `WHEN` |

**틀을 바꾸면 반드시 사용자에게 알린다**(§9).

### 2-2-0. 넉 장의 틀은 두 가지다 — 추천은 에이전트가, 결정은 사용자가

| 틀 | 쓰는 때 | 태그 |
|---|---|---|
| **이야기형** | 하나의 개념. 문제에서 출발해 해법으로 닿는 한 줄기가 있다 | `PROBLEM` `IDEA` `SOLUTION` `BENEFIT` |
| **나열형** | 여러 기법을 묶은 상위 개념. 한 줄기로 꿸 수 없다 | `IDEA 1` `IDEA 2` `IDEA 3` `IDEA 4` |

- **에이전트는 어느 쪽인지 판단해 추천하고, 그 근거를 한 줄로 댄다.** 예: "온톨로지 자식이 11개라
  한 줄기 이야기가 안 됩니다. 나열형을 권합니다."
- **고르는 것은 사용자다.** 추천만 하고 답을 기다린다. 혼자 정해서 넉 장을 그려 놓지 않는다.
- 판단 근거: 온톨로지에서 **자식이 여럿이고 서로 대등한 기법**이면 나열형, **하나의 메커니즘**이면 이야기형.

### 2-2-1. 나열형으로 정해졌으면 — `IDEA 1·2·3·4`

온톨로지에서 **자식이 여럿인 상위 개념**(예 `AdvancedPrompting` 11개)은 한 줄기 이야기가 아니다.
`PROBLEM → IDEA → SOLUTION → BENEFIT` 을 억지로 끼우지 말고 **대표 기법 네 개를 한 장에 하나씩** 그린다.

| 항목 | 규칙 |
|---|---|
| 태그 | `IDEA 1` `IDEA 2` `IDEA 3` `IDEA 4` |
| 제목 | `기법 이름 — 그 기법이 하는 일` 한 줄 (예: `생각의 나무 — 펼쳐 보고 막히면 되돌아간다`) |
| 밑줄 | 그 기법의 **원논문 수치** 한 개 (출처는 §1-4 규칙대로 확인) |
| 네 개 고르는 법 | ① 온톨로지의 자식일 것 ② 원논문에 수치가 있을 것 ③ **그림이 서로 겹치지 않을 것** |
| 나머지 자식 | 04 하위 개념 구획에 전부 남는다. 그림에 안 넣었다고 빼지 않는다 |
| 개요 | 묶음임을 첫 줄에 밝힌다 — "…방법들의 묶음이다" |

- 어느 네 개를 골랐고 **왜 골랐는지 한 줄로 밝힌다.** 고른 근거 없이 네 개를 정하지 않는다.
- 단일 개념이면 §2-1 의 `PROBLEM·IDEA·SOLUTION·BENEFIT` 을 그대로 쓴다.

### 2-3. 숫자 규칙

- **한 장에 숫자는 많아야 하나.** 나머지는 레퍼런스·체리로 보낸다.
- 숫자는 **조건과 함께** 읽히게 둔다. `68%`만 있으면 거짓말이 된다.

### 2-4. 그림에서 반드시 버리는 것

파이프라인 전체도 / 2×2 표 / 라이브러리 이름 나열 / 보조 수치 / 시간선 / 문제 3개 이상 나열.
〈왜〉 조사한 것을 다 넣으려다 요소가 늘었고, 요소가 많아 안 되니 통째로 걷어내다 그림을 죽였다.
**조사는 무엇이 중요한지 알기 위한 것이지 다 올리라는 뜻이 아니다.**

## 3. 그림 규칙

### 3-1. 시각 문법

- **사물 → 화살표 → 사물.** 그림은 *변화*를 보여야 한다.
  상태 나열(위 칸/아래 칸)은 이해되지 않는다. **표는 그림이 아니다.**
- 빈 사각형 금지. 모든 블록은 채워진 면에 **이름이 가운데**.
- 사람(스틱 피겨) 그리지 않는다.
- ✕·금지 기호로 상태를 말하지 않는다. **상태는 사물로 보여준다**
  (`OUTDATED` 꼬리표를 달고, 낡은 서랍을 뺀다).

### 3-2. 좌표 격자 (넉 장 공통)

| 항목 | 값 |
|---|---|
| viewBox | `0 0 340 142` |
| 사물 띠 | y **28 ~ 104**, 세로 중심 **66** |
| 이름표 기준선 | y **126** |
| 화살표 | y **66** 한 줄 |
| 카드 안 정렬 | `figure svg { margin-block: auto }` |

- 사물이 하나뿐인 장은 **다른 카드의 그림 높이에 맞춰 키운다.** 빈 여백을 남기지 않는다.
- 요소를 옮기면 **그 요소에 딸린 글자·구멍·화살표를 같은 값만큼 옮긴다.**

### 3-3. 색

| 색 | 뜻 | 토큰 |
|---|---|---|
| 체리 | 문제·실패 | `--cherry`, `--cherry-soft`, `--cherry-border` |
| 보라 | 색인·검색 | `--violet-soft`, `--violet`, `--violet-border` |
| 초록 | 이득·개선 | `--green-soft`, `--green` |

- **카드마다 색 하나.** 색은 장식이 아니라 분류다.
- 팔레트 밖의 색을 새로 만들지 않는다.
- 다크 모드: 모든 색은 **토큰으로만** 쓴다. 하드코딩한 색은 한쪽 테마에서 깨진다.

### 3-4. 굵기·글자

- **굵게는 카드당 하나** — 그 카드의 숫자. 이름표는 `font-weight="500"`.
- 크기: 이름 12~13 / 보조 9.5 / 마이크로 라벨 8.5(자간 1).

### 3-5. SVG 함정 (실제로 틀렸던 것)

| 함정 | 증상 | 대처 |
|---|---|---|
| 클래스의 `fill:none`이 `fill=` 속성을 이긴다 | 채운 줄 알았는데 투명 | `style="fill:var(--x)"` 인라인으로 |
| 회전(`rotate`) 쓰면 위치·정렬이 어긋난다 | 태그가 떠 보인다 | **회전을 쓰지 않는다** |
| 점·아이콘을 글자 옆에 두면 붙는다 | `●UTDATED` | 점을 빼거나 8px 이상 띄운다 |
| 텍스트 폭을 눈대중하면 넘친다 | 상자 밖으로 삐져나감 | 한글 ≈ font-size, 영문 ≈ 0.55×font-size로 계산 |
| 빈 도형(`width="0"`)을 남긴다 | 렌더 쓰레기 | 작업 후 `width="0"` 검색해 제거 |

### 3-6. 그린 뒤 눈으로 검토한다 (건너뛰지 않는다)

그림은 좌표를 맞췄다고 맞게 보이지 않는다. **발행한 화면을 확대해 넉 장을 한 장씩** 본다.
아래 열 가지를 모두 통과해야 다음으로 넘어간다. 하나라도 걸리면 고치고 **다시 보고** 넘어간다.

| # | 보는 것 | 자주 나는 고장 |
|---|---|---|
| 1 | 화살촉이 선의 진행 방향을 향하는가 | 방향과 무관한 삼각형이 붙어 있다 |
| 2 | 화살촉이 다음 도형을 파고들지 않는가 | 머리 끝이 상자 안으로 들어간다 |
| 3 | 각·호가 두 선 사이에 정확히 걸리는가 | 호가 원점에서 떨어져 혼자 떠 있다 |
| 4 | 각이 눈에 보일 만큼 벌어졌는가 | 10° 남짓이면 각으로 안 읽힌다 — **25° 이상** |
| 5 | 글자가 도형 밖으로 넘치지 않는가 | 긴 한글 라벨이 상자를 넘어간다 |
| 6 | 글자끼리, 글자와 선이 겹치지 않는가 | 점·기호가 글자에 달라붙는다 |
| 7 | 넉 장의 사물이 같은 높이에 서는가 | 한 장만 위로 뜨거나 작다 |
| 8 | 색이 카드당 하나인가 | 체리·보라·초록이 한 장에 섞인다 |
| 9 | 빈 도형·남은 조각이 없는가 | `width="0"` 같은 찌꺼기가 남는다 |
| 10 | 영문 토글에서도 1~9가 유지되는가 | 영문이 길어 상자를 넘는다 |

**검토 방법**: 발행된 링크를 열어 화면을 넓게 잡고(≈1100px) 그림 구획을 확대해 본다.
축소된 전체 화면만 보고 "괜찮다"고 넘기지 않는다 — 이번 사례에서 각과 화살촉 오류가
전체 화면에서는 보이지 않았다.

## 4. 문구 규칙

### 4-1. 쓰는 법

- **제목**: 사람들이 실제 쓰는 말로. 전문 용어는 하나까지.
  - ✗ "지식이 가중치 안에 갇혀 있다" (직관적이지 않다)
  - ✗ "다 외워 버려서 한 줄만 고칠 수가 없다" (어린애 말투)
  - ✓ "모델 지식은 학습한 지점에 멈춰있다"
- **그림 밑 한 줄**: 제목이 한 말을 반복하지 않는다. **사실이나 숫자만.** 가운데 정렬.
  - 출처를 앞세우는 서론 금지 — "원논문이 서론에서 가장 먼저 든 문제다 —"
- **Overview 2줄 공식**: `1줄 = 무엇을 하는가` + `2줄 = 그래서 무엇이 달라지는가`.
  약어는 첫 등장에 한국어 풀이를 괄호로 — `RAG(검색 증강 생성)`.

  **개요 쓰는 법 (건너뛰지 않는다):**
  1. 개념을 **충분히 조사한다** — 온톨로지 설명 전문 + 하위 개념 전부 + 원논문의 정의 문장.
     네 컷에 고른 기법 몇 개가 아니라 **묶음 전체**를 덮어야 한다.
  2. **다른 AI들에게 같은 질문을 던진다** (브라우저 도구). 로그인 없이 되는 곳:
     Gemini · ChatGPT · Perplexity. Grok 은 로그인을 요구하므로 계정을 만들지 말고 건너뛴다.
  3. 받은 답과 **내 초안을 나란히 놓고**, 무엇이 빠졌고 무엇이 번역투인지 한 줄로 짚는다.
  4. 그것들을 **총괄해 2문장 내외**로 만들어 사용자가 고르게 한다.
  - **"2줄"이 아니라 "2문장 내외"다.** 화면에서 몇 줄로 접히는지는 기준이 아니다.
  - **특정 기법 몇 개를 나열해 정의로 삼지 않는다.** 묶음 개념이면 더 그렇다 —
    11개 중 4개를 적으면 그 4개가 정의처럼 읽힌다.
  〈왜〉 개요는 페이지의 첫인상이고, 개념 전체를 대표하는 유일한 문장이다.
- **프롬프트 투 설명 금지.** 제품에 작업 지시서 같은 문장을 넣지 않는다.
  - ✗ "저서·논문·인터뷰에서 고른 문장. 기술 설명이 아니라 관점을 바꾸는 한 줄"

### 4-2. 언어 정책

| 무엇 | 한국어 화면 | 영문 화면 |
|---|---|---|
| 구획 이름 (`01 — Overview`) | 영문 그대로 | 영문 |
| 역할 태그 (`PROBLEM`) | 영문 그대로 | 영문 |
| 상태 라벨 (`OUTDATED`, `HALLUCINATION`) | 영문 그대로 | 영문 |
| 고유명 (`MODEL`, `FAISS`, `k = 5~10`) | 그대로 | 그대로 |
| 그 외 모든 문장·이름표 | 한국어 | 영어 |
| 인용문 | **번역문** | 원문 |
| 출처 줄 | 언어 중립 (`Madrona (2025-03-26)`) | 동일 |

- **SVG 안 글자까지** 토글을 따라야 한다. `${x("한국어","English")}` 형태로 쓴다.
- 한국어를 고치면 **영어도 같이 고친다.** 고친 뒤 §8-11 항목으로 확인한다.

### 4-3. 손대지 말 것

- **중복 금지**: 구획명 / 제목 / 그림 / 밑줄이 같은 사실을 두 번 말하지 않는다.
- **하나를 빼면 같은 성격을 전부 뺀다.** 한 장만 고치면 더 어색해진다.
- **사용자가 이미 보고 넘어간 문구는 지시 없이 고치지 않는다.** 그림을 고쳐 제목과
  안 맞아 보이면 고치지 말고 **그 사실만 말하고 묻는다.**

## 5. 체리스

### 5-0. 체리는 무엇을 담는 자리인가

**기술을 설명하는 자리가 아니다.** 설명은 그림과 밑줄이 맡는다. 체리는 읽는 사람의 마음에
남는 말을 담는다. 그래서 후보를 모을 때 아래 **세 가지에 점수를 매겨** 고른다.

| 축 | 무엇 | 0점 | 1점 | 2점 |
|---|---|---|---|---|
| **예지** | 미래가 어떻게 달라지는지 앞서 말한 문장 | 현재 사실만 | 방향을 암시 | 몇 년 앞을 꿰뚫음 |
| **영감** | 관점을 뒤집거나 한 번 더 생각하게 하는 문장 | 설명문 | 통찰이 하나 | 읽고 나면 보는 눈이 바뀜 |
| **재치** | 비유·역설·농담이 살아 있는 문장 | 건조함 | 비유가 있음 | 한 번에 기억에 박힘 |

- **한 축에서 2점이면 충분하다.** 세 축을 고루 채울 필요는 없다. 두루 1점짜리로 무난한 문장보다
  한 축에서 세게 치는 문장이 낫다 — 체리는 평균이 아니라 최고점으로 고른다.
- 정렬도 합계가 아니라 **가장 높은 축의 점수**로 한다. 같은 2점끼리는 축이 겹치지 않게 섞는다.
- **어느 축에서도 2점이 없으면(최고 1점) 후보에 올리지 않는다.** 그게 설명문을 걸러내는 선이다.
- 숫자만 말하는 문장(정확도 몇 %, 파라미터 몇 개)은 대개 세 축이 다 낮다 — 그런 사실은 **그림의
  숫자 자리**로 보낸다. 단, 숫자가 농담이나 역설의 재료라면 재치 2점이 된다.
  (예: "램이 넉넉하니 하드디스크는 필요 없다는 말과 같다", "1만분의 1만 학습한다")

### 5-1. 결과를 내는 방식 — 화면 + 문장 20개를 한 번에

**산출물은 둘이 한 묶음이다.**

1. **샘플 화면** — 추천 다섯을 넣어 완성해 발행한 링크
2. **문장 20개** — 아래 5·5·5·5 구성의 후보표

둘을 **같은 응답에** 낸다. 작업자는 화면을 보면서 표에서 번호를 골라 고친다.
화면만 내거나 표만 내면 작업자가 두 번 기다리고, 고칠 근거도 없다.
작업자가 번호를 주면 그대로 바꾸고 다시 발행한다 — 이 왕복이 한 개념의 마무리다.

### 5-1-1. 20개를 모으는 요령 (5·5·5·5)

- 에이전트가 혼자 추리지 않는다. 20개를 모아 보여주고 고르게 한다.
- **묶음별로 찾는 곳이 다르다.** 한곳만 뒤지면 한 묶음만 찬다.

  | 묶음 | 어디서 | 검색어 요령 |
  |---|---|---|
  | 미래지향 | 업계 리더의 에세이·기조연설·블로그 | `<개념> + 인명 + quote/keynote/essay`, 연도를 붙여 최근 것부터 |
  | 영감지향 | 원논문 초록·서론, 그 분야의 고전 | 논문 제목 + `abstract`, 고전은 책 제목 + 쪽수 |
  | 재치지향 | 인터뷰·팟캐스트·트윗·개인 블로그 | 비유어로 검색 — `like a`, `is just`, `secretly`, `hottest`, `last` |
  | 자유 | 위에서 넘친 것 + 인공지능 밖의 글(표시 필수) | — |

- **문장을 고르는 눈**: 비유(`~는 ~다`), 역설(`사실은 ~이다`), 숫자가 농담이 된 것(`1만분의 1`),
  시간을 건 선언(`앞으로 10년`), 자기 분야를 낮춰 부르는 말(`편법이다`) — 이런 모양이면 2점이다.
- **후보 20개 표는 선택이 아니라 산출물의 일부다.** "보여드릴까요"라고 묻지 않는다.
  페이지 하나를 냈는데 표가 없으면 그 작업은 끝난 것이 아니다.
- **한 번에 낸다.** 후보표를 먼저 보내고 답을 기다렸다가 페이지를 만들지 않는다 —
  추천 5개를 넣은 **완성된 화면과 후보 20개 표를 같은 응답에 함께** 낸다. 사용자는 보면서
  번호로 바꾼다. 작업을 두 번에 나누면 사용자가 두 번 기다린다.
- **구성 할당 — 축마다 최소 다섯 개씩 채운다.**

  | 묶음 | 최소 | 어디서 찾나 |
  |---|---|---|
  | 미래지향(예지) | **5개** | 업계 리더의 전망·에세이·기조연설·블로그 |
  | 영감지향 | **5개** | 원논문의 선언, 고전, 관점을 뒤집는 문장 |
  | 재치지향 | **5개** | 비유·역설·농담 — 인터뷰·팟캐스트·트윗 |
  | 자유 | 5개 | 위 셋 어디든. **이 묶음만 인공지능 밖에서 가져와도 된다 — 표에 `AI 밖`으로 표시** |

  한 묶음이 다섯을 못 채우면 **거기서 더 찾는다.** 다른 묶음을 늘려 20을 맞추지 않는다.
  논문 초록만 뒤지면 영감 묶음만 차고 미래·재치가 빈다 — 그때는 조사 범위가 잘못된 것이다.
- 표는 **묶음별로 나눠** 보여준다. 열: `#` · `발언자` · `연도` · `실릴 문장(번역)` · `예지·영감·재치 점수` · `출처 등급(A~D)` · `원문 확인 여부` · `범위`(인공지능 밖이면 `AI 밖 — <분야>`)
- 표 아래에 **에이전트의 추천 5개**를 번호로 찍고, 왜 그 다섯인지 한 줄씩 붙인다.
- 사용자가 번호로 고르거나 바꾸면 그대로 반영한다. **답이 없으면 추천 5개로 진행하고, 언제든
  번호만 말해도 교체·순서 변경이 된다고 알린다.**
- 20개를 못 채웠으면 채운 수만 보여주고 몇 개인지 밝힌다. 숫자를 맞추려 억지 후보를 넣지 않는다.
- 페이지에 실리는 것은 **5개 이하**다. 후보 표는 산출물이 아니라 고르기 위한 재료다.

### 5-2. 고르고 쓰는 규칙

- **5개 이하.**
- **그 기술을 직접 말하는 문장만.** 인접 분야의 일반적 비전은 안 된다 (후보 20개 중 15개는
  인공지능 관련 글로만 모은다 — §1-1).
  〈왜〉 Licklider·Engelbart의 명문장을 넣었다가 "RAG하고 관련 있냐"는 지적을 받았다.
  예외: **그 기술이 실현한 예언**은 맨 앞에 한 개까지(Bush의 메멕스 → RAG).
- 구성 권장: 예언/원류 1 + 원논문 1 + 현업의 말 2~3.
- 같은 사람은 **서로 다른 이야기를 할 때만** 둘까지.
- **한국어 화면에는 번역문**, 영문에 원문. 두 화면이 같은 영어면 번역을 안 한 것이다.
- 번역 규칙: 뜻을 살리되 직역투를 피한다. 원문 생략은 `…`, 보충은 `[ ]`로 표시한다.
- 인용문 밑에 해설을 붙이지 않는다. 문장 하나로 서게 한다.
- 출처 줄은 언어 중립으로.

## 6. 하위 개념 · 레퍼런스

### 6-1. 하위 개념은 온톨로지에서 읽어 온다 (추정 금지)

**반드시 DB를 직접 읽는다.** `nd-taxonomy.ts`·사이드바 라벨·핸드북 설명문은 참고용이고,
정본은 `handbook.concept` / `handbook.concept_relation` 이다.

```js
// apps/api 디렉터리에서 실행한다 (pg 모듈이 거기 있다). .env 의 LOCAL_DB_* 를 쓴다.
// 아래로(자식) = to_concept_id 가 이 노드인 행들의 from
SELECT r.relation_type::text rel, o.ontology_node, o.canonical_name, o.description
  FROM handbook.concept_relation r
  JOIN handbook.concept s ON s.id = r.to_concept_id   AND s.revoked_at IS NULL
  JOIN handbook.concept o ON o.id = r.from_concept_id AND o.revoked_at IS NULL
 WHERE s.ontology_node = :node AND r.revoked_at IS NULL
 ORDER BY r.relation_type, o.canonical_name;
-- 위로(부모) = from_concept_id 가 이 노드인 행들의 to  (selfCol/otherCol 을 바꾼다)
-- FULL/OUTLINE 판정: SELECT ontology_node FROM content.concept_page WHERE surface='learning'
```

- **노드 이름을 추측하지 않는다.** 사이드바 id(`chain-of-thought`)와 온톨로지 노드명
  (`AdvancedPrompting`)은 다르다. `content.concept_page` 에 등록된 `ontology_node` 를 먼저 보고,
  없으면 `handbook.concept` 에서 이름으로 찾는다. 후보가 둘 이상이면 **사용자에게 묻는다**
  (자식이 0개인 노드는 페이지를 걸 수 없으니 후보에서 빠진다).
- 카드에 넣는 값: **라벨 = `canonical_name`**, **관계 = `relation_type`**,
  **한 줄 설명 = `description` 을 줄인 것**. 라벨도 관계도 바꾸지 않는다.
  설명만 사람 말로 줄이고, 한국어·영어 양쪽을 쓴다.
- **자식이 많으면 다 넣는다.** 8칸에 맞추려고 자르지 않는다 (RAG 12개, AdvancedPrompting 11개).
  카드 격자는 2열이므로 개수는 제약이 아니다.
- 온톨로지에 없는 개념은 **넣지 않는다.** 넣어야 할 것 같으면 온톨로지에 추가하는 것이
  먼저이고, 그 추가는 사용자 지시 없이 하지 않는다 (DB는 프로덕션과 공유한다).

### 6-1-1. 오른쪽 Learning Roadmap — 기존 화면의 알고리즘을 그대로 쓴다

로드맵은 **새로 설계하지 않는다.** `apps/web/components/cherry/concept-reader-page.tsx` 의
`ConceptRoadmap` 을 그대로 옮긴다. 별도 데이터 없이 **하위 개념 하나로** 그린다.

| 항목 | 값 (기존 화면) |
|---|---|
| 띠 | `Prerequisites`(위) · `Go deeper`(아래) · `Related`(아래). **빈 띠는 생략** |
| 관계 매핑 | `PREREQUISITE` → Prerequisites · `SUBTOPIC`·`EXTENDS` → Go deeper · `RELATED`·`CONTRADICTS` → Related |
| 관계 종류 | **이 다섯뿐이다** — `SUBTOPIC` `PREREQUISITE` `EXTENDS` `RELATED` `CONTRADICTS` (`lib/api.ts` `ConceptRelationType`) |
| 중앙 상자 | **온톨로지 노드명**(`doc.node`, 예 `AdvancedPrompting`). 표시 이름이 아니다. 아래에 `(you are here)` |
| 칩 | 이름 길이에 맞춰 폭이 늘고, 폭이 남으면 **옆에 나란히**, 모자라면 다음 줄. 줄은 가운데 정렬 |
| 글자 | 폭에 맞춰 ①그대로 → ②폰트 축소 → ③줄바꿈(공백·camelCase 경계). **자르지 않는다** |
| 페이지 없음 | 칩 테두리를 파선 |
| 화살표 | 위→중앙 실선, 중앙→아래 **점선** |
| 폭 | `W=200` |
| 범례 | 4줄 고정 — Cherry/Violet/Dashed/Gray |

- **없는 관계를 만들지 않는다.** 상위 개념(부모)은 기존 화면의 로드맵에 **올라가지 않는다**
  — API 의 `childConcepts` 는 아래 방향 간선만 담기 때문이다.
  〈왜〉 `PARENT` 라는 관계와 `ABOVE` 띠를 지어내 넣었다가 전부 걷어냈다. 그런 관계 종류는 없다.

### 6-2. 레퍼런스

- **외부 링크만** 4개. 내부 개념 연결은 하위 개념 구획이 맡는다.
- 단계: `원전 / 입문 / 논쟁 / 실전`. 해당 단계가 없는 주제면 그 칸을 비우지 말고
  `원전 / 입문 / 실전 / 확장`처럼 **주제에 맞는 4단계로 바꾼다.**
- 소개 한 줄은 "어디를 어떻게 읽으면 되는지"를 말한다.

## 7. 제작 순서

1. **S0 조사** — §1. 확인한 문장·수치·URL을 한곳에 적는다. 중단 조건(§1-3)을 지킨다.
2. **S1 틀 결정** — §2-2-0 으로 이야기형·나열형 중 어느 쪽인지 **추천하고 사용자의 답을 받는다.**
   정해진 틀의 네 칸에 하나씩 배치하고 **버릴 것을 명시**한다.
3. **S2 체리 후보** — 후보 20개를 추려 둔다(§5-1). 여기서 멈추지 않고 추천 5개로 계속 간다.
4. **S3 문구** — 제목 4 + 밑줄 4 + 개요를 **그림보다 먼저** 쓴다.
   개요는 §4-1 의 네 단계(조사 → 다른 AI 질의 → 비교 → 총괄)를 **전부** 거친다.
5. **S4 그림** — §3 격자로 넉 장. 그리기 전에 "이 그림이 한 문장으로 요약되나"를 묻는다.
6. **S5 확인** — 발행하고 **§3-6 눈검토 열 가지**를 넉 장에 적용한다. 좌표만 고치고 넘어가지 않는다.
   - 1회차: 전체 화면. 정렬·높이·색을 본다.
   - 2회차: 영문 토글 화면. 언어 혼입을 본다.
   - 고칠 것을 **모아서 한 번에** 고치고 재발행한다. 한 건씩 고쳐 여러 번 올리지 않는다.
7. **S6 검증** — §8 체크리스트를 확인 방법대로 통과시킨다.
8. **S7 인계** — 완성 화면 링크 **+ 체리 후보 20개 표**를 한 응답에 함께 낸다. 그리고 링크, 무엇을 근거로 무엇을 버렸는지, 수치가 없으면 없다는 사실을 적는다.

## 9. 승인 게이트 — 반드시 묻는 것

| 언제 | 무엇을 묻나 |
|---|---|
| 구획 이름을 바꾸거나 추가할 때 | 이름 후보와 이유 |
| 네 칸 틀을 대안 틀로 바꿀 때 | 어떤 틀로, 왜 |
| 페이지 제목(아티팩트 이름)을 정할 때 | 후보 제시, **임의로 짓지 않는다** |
| 개요 문장을 정할 때 | 후보 2~3개를 나란히 |
| 체리를 고를 때 | **후보 20개 표 + 추천 5개**를 보여주고 고르게 한다 |
| 이미 보여 준 문구를 고쳐야 할 때 | 무엇이 왜 안 맞는지만 말하고 대기 |
| 커밋·배포 | 하지 않는다. 사용자가 한다 |

## 10. 하지 말 것 (판정 가능한 기준)

| 하지 말 것 | 판정 기준 | 어떤 일이 있었나 |
|---|---|---|
| 조사 수치 전부 넣기 | 한 그림에 숫자 2개 이상 | 지저분해져 결국 전부 걷어냈다 |
| 지적마다 국소 수정 | 같은 그림을 3회 이상 부분 수정 | 요소를 덜어내다 라벨만 남았다 |
| 손그림·기울인 도형 | `rotate(` 사용, 곡선 장식 | "초딩 낙서" 소리를 들었다 |
| 아이콘으로 때우기 | 한 그림에 아이콘 3개 이상 | 뜻이 안 읽힌다 |
| 구획 안에 글자만 있는 카드 | 넉 장 중 SVG 없는 카드 | 세트가 깨진다 |
| 부연으로 설명 메우기 | 밑줄이 제목의 다른 표현 | 정보량이 오히려 줄었다 |
| 승인된 문구 임의 변경 | 사용자가 준 문장을 다듬음 | 처음부터 다시 검토하게 만든다 |
| 확인 없이 반복 발행 | 스크린샷 없이 2회 이상 발행 | 정렬이 어긋난 채 여러 번 올라갔다 |
