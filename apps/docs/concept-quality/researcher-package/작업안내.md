# 개념 페이지 콘텐츠 작성 — 작업 안내

> 받는 분: 리서처 · 보내는 분: 개발 · 기준일 2026-08-19
> 같이 받은 파일: **`concepts-to-fill.json`** (305개 개념)
> **DB는 건드리지 않으셔도 됩니다.** JSON만 채워서 주시면 개발자가 DB에 반영합니다.

---

## 1. 이게 무슨 일인가

저희 사이트는 AI 개념 하나당 **설명 페이지 한 장**을 보여줍니다. 지금 **305개 페이지가 자동으로 만들어져 있는데, 내용이 대부분 비어 있습니다.**

그 빈 곳을 채우는 일입니다.

## 2. 페이지 한 장은 이렇게 생겼습니다

```
   [BASICS]                        ← 자동
   RAG                             ← 자동

   01  Overview          이 개념이 뭔지 설명하는 글      ← ✏️ 채워주세요
   02  Cherries          책에서 뽑은 핵심 내용들        ← ✏️ 채워주세요
   03  Child Concepts    관련 개념 목록                ← 자동 (건드릴 것 없음)
   04  References        읽는 순서를 매긴 참고자료      ← ✏️ 채워주세요
```

**채우는 곳은 4군데(①②④ + 작업자 이름)** 입니다. ③은 시스템이 자동으로 만듭니다.

---

## 3. 세 가지가 각각 무엇인가

### ① Overview — "이게 뭔데?"

문단 3개를 씁니다.

| 칸 | 무엇을 쓰나 |
|---|---|
| `definition` | 이 개념이 **무엇인지** |
| `whyItMatters` | **왜 중요한지** — 이걸 모르면 뭐가 곤란한지 |
| `context` | **실제로 뭘 하게 되는지** — 일의 모양 |

### ② Cherries — "책은 뭐라고 하나"

여러 책에서 **가장 좋은 한 조각씩** 뽑아 담는 것입니다. 이름이 '체리'인 이유입니다.

**규칙 두 가지가 전부입니다:**

**규칙 1 — 출처가 반드시 있어야 합니다.** 어느 책 몇 장에서 나온 말인지 적어주세요. 출처 없는 내용은 쓸 수 없습니다.

**규칙 2 — 서로 겹치지 않아야 합니다.** 세 권이 다 "RAG는 검색해서 붙이는 것"이라고만 하면 체리 3개가 아니라 1개입니다. 각각 **다른 각도**여야 하고, 합치면 그 개념이 대체로 다 설명되어야 합니다.

```
좋은 예 (RAG)
  · 왜 필요한가        → 지식이 오래돼서
  · 뭐가 성능을 좌우하나 → 문서 자르는 방식
  · 실무에선 뭐가 문제  → 검색 정확도 60% → 85%
  → 겹치지 않으면서 합치면 RAG가 설명됨
```

### ④ References — "뭘 어떤 순서로 읽나"

**순서가 있는 읽기 목록**입니다. 그냥 좋은 자료 나열이 아닙니다.

각 항목에 **"앞의 것이 안 다룬 무엇을 이게 채워주는가"** 를 적어주세요. 순서를 바꿔도 상관없다면 순서표가 아닙니다.

```
START HERE  → 가장 쉽고 넓게 다루는 것
NEXT →        앞의 것이 안 다룬 것
THEN →        더 깊이
DEEP DIVE →   전문가용
```

## 4. JSON 파일 보는 법

**305개 항목이 전부 같은 18개 필드**를 갖습니다. 값이 있으면 이미 채워진 것, 비어 있으면 채울 곳입니다.

```jsonc
{
  // ── 식별 · 수정 금지 ──
  "node": "Chunking",              // ⚠️ 시스템 연결 열쇠. 절대 수정 금지
  "name": "Chunking",              // 온톨로지 내부 이름
  "priority": "B",                 // A → B → C 순으로 작업 (D 는 하지 마세요)

  // ── 작업량 ──
  "toFillCount": 6,                // 아직 채워야 할 필드 수. 0 이면 완료
  "toFillList": [                  // ✏️ 이 필드들을 채워주세요
    "displayTitle", "overview.definition", "overview.whyItMatters",
    "overview.context", "cherries", "references"
  ],

  // ── 이 페이지가 어떻게 보이나 · 자동 ──
  "menuSection": null,             // BASICS | ADVANCED | null(메뉴에 없음)
  "menuLabel": null,
  "pageType": "LINKED",            // MENU | LINKED | UNREACHABLE
  "depthFromMenu": 1,              // 메뉴에서 몇 단계 들어가야 나오나
  "reachableFromMenus": ["RAG", "Embeddings"],
  "shownAsCardOn": ["Embedding", "RAG", "Tokenization"],

  // ── 참고 정보 · 자동 · 수정 금지 ──
  "bookParagraphsAvailable": 34,   // ⭐ 우리 자료에 관련 문단이 34개
  "bookSearchTerms": [ … ],        // ⭐ 책에서 찾을 때 쓸 검색어
  "ontologyDescription": "…",      // 지금 화면에 자동으로 뜨는 설명 (한글일 수 있음)
  "childConcepts": [ … ],          // 03 섹션 — 자동 생성. 채울 필요 없음

  // ── ✏️ 여기부터 작성 대상 ──
  "displayTitle": "",              // 비었음 → 채우기
  "overview": { "definition": "", "whyItMatters": "", "context": "" },
  "cherries": [ { "source": "", "locator": "", "chunkId": "", "insight": "" }, … ],
  "references": [ { "order": 1, "stage": "START HERE", "title": "", … }, … ],
  "contributors": [                // 누가 작업했는지
    { "name": "", "role": "Author" },
    { "name": "", "role": "Evidence sourcing" }
  ]
}
```

**이미 채워진 개념은 같은 자리에 실제 값이 들어 있습니다.** 예를 들어 `RAG` 는 `toFillCount: 0`, `displayTitle: "Retrieval-Augmented Generation (RAG)"`, `cherries` 에 7건이 그대로 들어 있습니다. **완성 예시로 참고하세요.**

작업 순서는 이렇게 하시면 됩니다:
1. `priority` 가 `A` 인 것부터 (11개)
2. `toFillCount` 가 0 이 아닌 항목만
3. `toFillList` 에 적힌 필드를 채움
4. 각 필드 규칙은 **§5-A 필드 명세** 참고

### ⭐ `page.type` — 이 페이지가 사용자에게 보이는가

```jsonc
"page": {
  "type": "LINKED",                            // MENU | LINKED | UNREACHABLE
  "depthFromMenu": 1,                          // 메뉴에서 몇 단계 들어가야 나오나
  "reachableFromMenus": ["RAG", "Embeddings"], // 어느 메뉴에서 갈 수 있나
  "shownAsCardOn": ["RAG", "Embedding"]        // 어느 페이지에 카드로 뜨나
}
```

| 값 | 뜻 | 작업 |
|---|---|---|
| `MENU` | 왼쪽 메뉴에서 **바로 열리는** 페이지 | **제일 급합니다** |
| `LINKED` | 메뉴 페이지에서 **링크를 타고** 들어가야 나옴 | 그다음 |
| `UNREACHABLE` | 지금은 **어느 화면에서도 안 뜸** | **하지 마세요** (226개) |

`depthFromMenu` 가 `1` 이면 메뉴 페이지에 **카드로 바로 보이는** 개념이라 눈에 잘 띕니다.
`shownAsCardOn` 에 여러 페이지가 적혀 있으면 그만큼 여러 곳에서 보인다는 뜻이라 우선순위가 높습니다.

### ⭐ `bookParagraphsAvailable` · `bookSearchTerms` 를 먼저 보세요

```jsonc
"bookParagraphsAvailable": 65,
"bookSearchTerms": ["AdvancedPrompting", "ChainOfThought", "PAL", "ReAct",
                    "TreeOfThoughts", "SelfConsistency", …]
```

**`bookParagraphsAvailable`** 은 **우리 자료에서 이 개념에 관련된 문단이 몇 개인지** 미리 세어둔 숫자입니다.

| 숫자 | 뜻 |
|---|---|
| 10개 이상 | 체리를 넉넉히 뽑을 수 있습니다 |
| 3~9개 | 가능하지만 각도가 부족할 수 있습니다 |
| 0~2개 | **체리를 비워두세요** (아래 참고) |

**`bookSearchTerms`** 는 **책에서 그 근거를 찾을 때 쓸 검색어**입니다. 꼭 이걸 쓰세요.

> ⚠️ **개념 이름으로만 찾으면 못 찾습니다.**
> 예를 들어 `Advanced Prompting` 은 책에 그 표현이 **한 번도 안 나옵니다.** 대신
> `Chain-of-Thought`, `PAL`, `ReAct`, `Tree of Thoughts` 같은 **개별 기법 이름**으로 서술됩니다.
> 그래서 개념명만으로 세면 0건이지만, 하위 개념명까지 넣으면 **65건**입니다.
> `bookSearchTerms` 에 그 이름들이 들어 있습니다.

## 5. 채우는 형식 — 실제 예시

RAG 하나가 **이미 채워져 있습니다.** JSON에서 `"node": "RAG"` 를 찾아 `filled` 부분을 보시면 형식이 그대로 나옵니다.

### Cherries 예시
```jsonc
{
  "source":  "AI Engineering",                              // 책 이름
  "locator": "Chapter 6. RAG and Agents › Retrieval Optimization",  // 어디에
  "insight": "Context reranking is not search reranking. In search, the exact rank of a result is what matters. In context, order still matters but for a different reason — models process documents at the beginning and end of a context better than those buried in the middle."
}
```

### References 예시
```jsonc
{
  "order": 1,
  "stage": "START HERE",
  "title": "AI Engineering — Ch.6 \"RAG and Agents\"",
  "url": null,                    // 우리 책이면 null, 외부 자료면 주소
  "inLibrary": true,              // 우리 책이면 true
  "byline": "Chip Huyen",
  "teaches": "The retrieval-first mental model, and why chunking and reranking decide output quality more than model choice does.",
  "addsOverPrevious": "foundational mental model"   // 앞의 것 대비 더해주는 것
}
```

## 5-A. 필드 명세 — 타입 · 길이 · 필수 여부

> ⚠️ 아래를 어기면 **저장이 실패하거나 화면에 안 뜹니다.** 형식이 조금이라도 다르면 조용히 누락됩니다.

### 수정 금지 (읽기 전용)

| 필드 | 타입 | 설명 |
|---|---|---|
| `node` | 문자열 | **DB 연결 열쇠.** 절대 수정 금지 |
| `name` `priority` `toFillCount` `toFillList` | — | 자동 계산 |
| `menuSection` `menuLabel` `pageType` `depthFromMenu` | — | 자동 |
| `reachableFromMenus` `shownAsCardOn` | 배열 | 자동 |
| `bookParagraphsAvailable` | 숫자 | 자동 |
| `ontologyDescription` | 문자열 | 자동 (현재 화면에 뜨는 설명) |
| `childConcepts` | 배열 | 자동 (03 섹션) |

### ✏️ 작성 대상

#### `displayTitle` — 화면 제목
| | |
|---|---|
| 타입 | 문자열 |
| 필수 | **예** (비면 `RedTeaming` 같은 코드명이 그대로 노출) |
| 길이 | **권장 60자 이내** (DB 제한은 없으나 넘으면 제목이 두 줄로 깨짐) |
| 예 | `"Retrieval-Augmented Generation (RAG)"` (36자) |
| 주의 | 줄바꿈 금지 |

#### `overview` — 3문단
| 칸 | 타입 | 필수 | 길이 | 내용 |
|---|---|---|---|---|
| `definition` | 문자열 | 예 | 200~400자 | 이 개념이 무엇인지 |
| `whyItMatters` | 문자열 | 예 | 200~400자 | 왜 중요한지 |
| `context` | 문자열 | 예 | 150~350자 | 실제로 뭘 하게 되는지 |

- **문단 안에서 줄바꿈(`\n`)을 쓰지 마세요.** 시스템이 세 칸을 문단 3개로 합칩니다.
- `**굵게**` 표시는 쓸 수 있습니다.
- RAG 실제 길이: 정의 322자 · 왜 중요 296자 · 맥락 233자 (총 909자)

#### `cherries` — 배열
| 칸 | 타입 | 필수 | 규칙 |
|---|---|---|---|
| `source` | 문자열 | **예** | **우리 책 4권 중 하나의 정확한 제목** (아래 목록) |
| `locator` | 문자열 | **예** | `챕터 › 절` 형식. 예: `"Chapter 6. RAG and Agents › Retrieval Optimization"` |
| `chunkId` | 문자열(UUID) | **⚠️ 아래 참고** | 원문 문단 식별자 |
| `insight` | 문자열 | **예** | **150~350자** 권장. RAG 실제: 255~299자 |

> **화면에는 두 가지가 더 붙습니다 (자동이라 적지 않으셔도 됩니다)**
> - **저자** — `source` 로 지정한 자료의 저자가 자동으로 붙습니다 (예: `AI Engineering` → Chip Huyen)
> - **정리 여부** — `insight` 를 쓰시면 "정리된 문장", 비우면 원문이 그대로 노출됩니다

**⚠️ `chunkId` 에 대하여**
시스템은 체리를 **우리 책의 특정 문단**에 붙여서 저장합니다. `chunkId` 는 그 문단의 식별자입니다.
- **모르시면 빈 문자열(`""`)로 두세요.** 개발자가 `source`·`locator` 를 보고 찾습니다.
- 그러려면 `locator` 를 **최대한 정확히** 적어주셔야 합니다. 한 챕터에 문단이 **69~149개** 있어서, 절(節) 이름까지 없으면 찾기 어렵습니다.
- **같은 문단을 한 개념에 두 번 인용할 수 없습니다.** 체리마다 다른 문단이어야 합니다.

**허용되는 `source` 값 (이것만 가능)**
| 정확한 제목 | 저자 | 문단 수 |
|---|---|---:|
| `Building Applications with AI Agents` | Michael Albada | 1,248 |
| `AI Engineering` | Chip Huyen | 935 |
| `LLM Engineers Handbook` | — | 776 |
| `Reflexion` (논문) | — | 95 |

→ **이 4개 외의 출처로는 체리를 만들 수 없습니다.** 외부 자료는 References 에 넣어주세요.

#### `references` — 배열
| 칸 | 타입 | 필수 | 규칙 |
|---|---|---|---|
| `order` | **숫자** | 예 | 1, 2, 3, 4 … 순서대로 |
| `stage` | 문자열 | 예 | **`START HERE` / `NEXT →` / `THEN →` / `DEEP DIVE →`** 중 하나 (화살표 포함) |
| `title` | 문자열 | 예 | 자료 제목. 권장 70자 이내 |
| `url` | 문자열 **또는 `null`** | 예 | 외부 자료면 `https://…`, 우리 책이면 **`null`** (빈 문자열 `""` 아님) |
| `inLibrary` | **참/거짓** | 예 | 우리 책이면 `true`, 외부면 `false` |
| `byline` | 문자열 또는 `null` | 아니오 | 저자. 없으면 `null` |
| `teaches` | 문자열 | 예 | 무엇을 배우나. 100~200자 |
| `addsOverPrevious` | 문자열 | 예 | **앞의 것 대비 더해주는 것.** 짧게 (20~60자) |

- ⚠️ **`url` 은 빈 문자열이 아니라 `null`** 이어야 합니다. `""` 로 두면 화면에서 깨진 링크가 됩니다.
- ⚠️ **`inLibrary` 는 문자열 `"true"` 가 아니라 참/거짓 값** `true` 입니다.
- ⚠️ 필드 이름을 **하나라도 다르게 쓰면 화면에 조용히 안 뜹니다.** 대소문자까지 정확히.

#### `contributors` — 작업한 사람
| 칸 | 타입 | 필수 | 규칙 |
|---|---|---|---|
| `name` | 문자열 | **예** | 이름 또는 GitHub 아이디. 예: `"tomatojams"` |
| `role` | 문자열 | 예 | **아래 4개 중 하나만** (이미 채워져 있으니 그대로 두세요) |

**허용되는 `role` 값**
| 값 | 무엇을 한 사람 |
|---|---|
| `Author` | **Overview 를 쓴 사람** |
| `Evidence sourcing` | **Cherries 를 찾은 사람** |
| `Lead reviewer` | 전체를 검수한 사람 |
| `Concept mapping` | 개념 관계를 정리한 사람 (보통 자동이라 비워둠) |

- 한 사람이 두 역할을 다 했으면 **두 줄 모두에 같은 이름**을 적으시면 됩니다.
- 해당 없는 역할은 `name` 을 빈 문자열로 두세요.
- 이 이름은 화면 오른쪽 **Knowledge Team** 카드에 표시됩니다.

## 6. 꼭 지켜주실 것

| # | 규칙 | 이유 |
|---|---|---|
| 1 | **`node` 값은 절대 수정하지 마세요** | 시스템이 이걸로 DB와 연결합니다 |
| 2 | **`toFill` 안만 채우세요** | `filled`·`hints`·`status` 는 참고용입니다 |
| 3 | **모르면 비워두세요** | 채우려고 지어내면 안 됩니다. 이 서비스의 가치가 "책이 실제로 하는 말"입니다 |
| 4 | **체리엔 출처를 꼭** | `source` 와 `locator` 없으면 못 씁니다 |
