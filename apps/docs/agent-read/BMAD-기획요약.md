# BMAD식 기획 플레이북 (초기 생성용)

> **언제  쓰나:** **아이디어에서 시작할 때** — "무엇을 만들지"가 아직 불명확한 신규 과제의 **기획 초기 생성**.
> **언제 안 쓰나:** "무엇을 만들지"가 정해진 정의된 기능·수정(크래시 수정, 의뢰사 요구 기능)엔 **불필요**(넓이 기획이 여분).
> **BMAD 툴 설치·실행 불필요.** 이 문서를 **플레이북 겸 템플릿**으로 쓴다. (여기 내용은 BMAD-METHOD의 방식을 요약·적응한 것이며, 원문 세부는 버전에 따라 다를 수 있음.)
> **검증 규율(중요):** 여기 생성물은 그럴듯한 문서("장식")가 아니라 **근거가 있거나 "미확인/가정"으로 표시**된 것이어야 한다(작업지침 §1-10). **생성은 BMAD식으로, 검증은 이 하네스로**(S3·S0.5·테스트 게이트).

---

## 0. BMAD 한눈에 — 두 핵심 혁신

1. **에이전트 기획(Agentic Planning)** — 전문 역할(분석·PM·아키텍트)이 **사람과 문답하며** 일관된 PRD·아키텍처 문서를 만든다. 요점은 "혼자 지어내기"가 아니라 **구조화된 엘리시테이션(질문으로 구체화)**.
2. **컨텍스트 내장 개발(Context-Engineered Dev)** — 기획을 **자기완결적 "스토리"**로 쪼갠다. 각 스토리에 그걸 구현하는 데 필요한 맥락(요구·관련 설계·파일 위치·기준)을 **통째로 박아** 넣어, 구현 에이전트가 컨텍스트를 잃지 않게 한다.
   - ⭐ **약한 모델(Qwen 27B)에 특히 유효** — 스토리가 자기완결적이면 모델이 여기저기 참조하다 헤맬 일이 준다. **이 하네스가 BMAD에서 가장 가져올 만한 기능.**

## 1. 역할·산출물 흐름 (알맹이만)

| 순서 | 역할 | 하는 일 | 산출물 |
|---|---|---|---|
| 1 (선택) | **분석(Analyst)** | 브레인스토밍·시장/경쟁 조사·문제 정의 | **프로젝트 브리프** |
| 2 | **PM** | 브리프 → 요구·성공기준·에픽/스토리 | **PRD** |
| 3 | **아키텍트(Architect)** | PRD → 기술스택·시스템설계·데이터·API·소스트리·코딩기준 | **아키텍처 문서** |
| 4 (선택) | **UX** | 화면 흐름·UI 스펙 | 프론트 스펙 |
| 5 | **PO(검수)** | 마스터 체크리스트로 문서 **정합·완결성 검증**, 에픽/스토리로 **분할(shard)** | 검증된·분할된 문서 |
| 6 (반복) | **SM → Dev → QA** | SM이 다음 **스토리**를 맥락 내장해 작성 → Dev 구현 → QA 검토 | 스토리 파일 → 코드 → 게이트 |

> 이 하네스에선 **1~5(생성)만 BMAD식으로** 쓰고, **6(구현·검증)은 이 하네스의 S3·S4·S5**로 대체한다. (BMAD의 Dev·QA보다 이 하네스 검증이 강하므로.)

## 2. 핵심 기능별 활용 (템플릿)

### 2-1. 구조화 엘리시테이션 (혼자 지어내지 않기)
불명확한 곳은 **번호 붙인 선택지로 사용자에게 물어** 구체화한다. 예:
> "인증 방식 후보: ① 세션 쿠키 ② JWT ③ OAuth 위임. 트레이드오프는 …. 어느 쪽?"
- 사용자 답이 없는 가정은 문서에 **"미확인/가정"** 으로 남긴다(§1-10). 지어낸 시장 수치·사용자 니즈를 사실처럼 쓰지 않는다.

### 2-2. 프로젝트 브리프 (분석) — 채울 뼈대
```markdown
## 문제
- 무엇이 문제인가 / 지금은 어떻게 처리되나(기존 대안)
## 사용자·이해관계자
- 누가 쓰나, 각자 무엇을 원하나
## 맥락·제약
- 시장·환경·기술 제약 (추측이면 "미확인")
## 목표(한 문장)
```

### 2-3. PRD (PM) — 채울 뼈대
```markdown
## 목표(Goals)            — 이 제품이 이루려는 것 (측정 가능하게)
## 배경(Background)        — 왜 지금, 왜 이것
## 요구사항
- 기능요구 FR1, FR2 …     — "시스템은 ~한다"
- 비기능요구 NFR1 …       — 성능·보안·가용성 등
## 스코프 경계             — 하는 것 / 안 하는 것(무엇을 뺐나)
## UI 목표(있으면)
## 기술 가정(Assumptions)
## 에픽 목록               — 각 에픽 = 배포 가능한 가치 증분
### 에픽 1: <제목>
- 스토리 1.1: <as a ~, I want ~, so that ~>
  - 인수기준(AC): 1) … 2) …   ← 측정 가능·검증 가능하게
```

### 2-4. 아키텍처 (아키텍트) — 채울 뼈대
```markdown
## 기술 스택               — 언어·프레임워크·DB·인프라 (버전까지)
## 시스템 설계             — 주요 컴포넌트·데이터 흐름
## 데이터 모델             — 핵심 엔티티·관계
## API/인터페이스          — 주요 엔드포인트·계약
## 소스 트리               — 폴더/파일 배치 규칙
## 코딩 기준·제약          — 규칙, 알려진 리스크
## 핵심 결정과 이유        — 택한 것 + 택하지 않은 대안과 그 이유
```

### 2-5. 에픽·스토리 분해 규칙
- **에픽 = 배포 가능한 세로 증분**(그 자체로 end-to-end 가치). 인프라만 만드는 에픽 금지.
- **스토리 = AI 한 세션에 끝낼 수 있는 세로 슬라이스** + **인수기준(AC)**.
- **스토리는 자기완결적으로**(2-6). 이 하네스에선 이게 곧 feature `구현서`의 STEP + `검수표`의 AC가 된다.

### 2-6. 컨텍스트 내장 스토리 — 채울 뼈대 (⭐ 핵심)
```markdown
# 스토리 <n>: <제목>
## 목표        — 무엇을 왜
## 인수기준(AC) — 무엇을 만족하면 done (검증 가능하게)
## 필요한 맥락 (이 스토리 안에 통째로)
- 관련 요구(FR/NFR):
- 손댈 파일·함수·경로:
- 관련 설계·데이터 모델·API 계약:
- 지켜야 할 코딩 기준·제약:
- 재사용할 기존 함수(그 부작용·스코프까지):   ← 낡은 가정 금지(§1-9·강화로그)
## 하지 말 것 / 스코프 밖
## 테스트 방법  — 이 스토리를 어떻게 검증하나
```
> 요점: **구현자가 다른 문서를 안 뒤져도 이 한 장으로 끝나게.** 약한 모델일수록 이 자기완결성이 실패율을 낮춘다.

### 2-7. 마스터 체크리스트 (PO 검수) — 분할 전 정합 확인
- PRD ↔ 아키텍처가 서로 모순 없나 / 에픽·스토리가 목표를 다 덮나 / 각 스토리에 AC가 있나 / 스코프 경계가 명확한가.
- (이 하네스의 **S3 L6 누적정합·목적정렬**과 같은 취지 — BMAD 산출물에도 한 번 돌린다.)

## 3. 이 하네스와의 접속 (BMAD 산출물이 어디로 가나)

| BMAD 산출물 | 이 하네스에서 | 
|---|---|
| 프로젝트 브리프·PRD의 배경·목표·범위 | `docs/plan/기획서` 또는 feature `지침`의 배경·범위 |
| 에픽·스토리 + AC | feature `구현서`의 STEP + `검수표`의 항목·완료기준 |
| 아키텍처 문서 | feature 폴더 또는 `agent-read` 파악 문서 |
| PO 마스터 체크리스트 | **S3 L6**(정합·목적정렬)로 대체·강화 |

**절차:** BMAD식으로 브리프→PRD→아키텍처→스토리를 **초기 생성** → 그다음 **정상 하네스 진입**: S0.5 조기관측(가정 검증) → S2 검수표 → **S3 적대적 검토** → S4 구현 → S5 검증.

## 4. 주의 (BMAD를 그대로 신뢰하면 안 되는 이유)

- BMAD의 넓은 문서는 **검증받지 않은 생성물**이라, 정의된 작업에선 결과를 거의 안 바꾼다("안 한 거랑 비슷"). **실패는 넓이 부족이 아니라 검증 부족에서 온다.**
- 그래서 이 문서는 **초기 생성(0→1 프레이밍)** 에만 쓰고, 이후 정확성은 **이 하네스의 검증**이 책임진다. **생성은 여기, 검증은 하네스.**
